## 1. Назначение и нормативность

Программа предназначена для человека без опыта программирования. Цель — сформировать устойчивое понимание Python, самостоятельность в решении практических задач и готовность объяснять решения на техническом собеседовании уровня Junior. Готовность к собеседованию не гарантирует трудоустройство: требования вакансий различаются.

В документе **«обязательно»** означает требование к будущей программе или её приёмке; **«рекомендуется»** — изменяемое методическое решение. Численные пороги ниже являются обязательными критериями этой спецификации, а не статистически подтверждёнными отраслевыми стандартами. Изменение обязательного критерия требует отдельного решения владельца курса и обновления версии спецификации. Материалы и утверждённый учебный план изменяются в соответствии с правилами проекта; сам план этот документ не утверждает.

**Обязательно:** язык материалов — русский, английские технические термины приводятся рядом с переводом при первом употреблении. Изложение идёт от простого к сложному, с явным указанием необходимых предварительных знаний. На каждом уровне сохраняется глубина понимания, а не только охват терминов.

### Адресный пересмотр обязательных требований в версии 1.1

1. **Добавлено:** подробная теория обязательна для каждой малой подтемы с постоянным ID, а не только для темы целиком (разделы 5–6). **Причина:** крупный обзор не позволяет проверить полноту объяснения механизма и предварительных знаний каждой подтемы.
2. **Добавлено и формализовано:** для каждого модуля обязательны исходник слайдов, карта соответствия результатам, подтемам и задачам, банк задач и анализа кода, интервью-вопросы с рубриками, контроль и материал для повторения (разделы 5–6, 10). Часть этих видов ранее называлась рекомендуемой, хотя связанные критерии проверки уже требовали их; теперь обязательный комплект указан явно. **Причина:** модуль должен быть пригоден для полного цикла обучения и контроля, а покрытие — проверяемым.
3. **Добавлено:** после каждого объясняющего блока малой подтемы обязательна посильная задача на уже объяснённом материале; в слайдах такой же порядок (разделы 5–6). **Причина:** немедленное применение выявляет непонимание до перехода к следующему механизму. Один ID задачи может использоваться в теории и слайдах без дублирования самой задачи или минут работы.
4. **Добавлено:** проверка категорий задач по модулю и их сложности; отсутствие категории требует обоснования (раздел 6). **Причина:** уже принятая цепочка материалов различает простые, средние, сложные и интервью-задачи, а спецификация должна позволять проверить её полноту.
5. **Уточнено:** постоянный ID обязателен для каждого результата, подтемы, слайда, вопроса и задачи (раздел 10). **Причина:** карта покрытия и ссылки между материалами проверяются только при устойчивых адресах; формат учитывает уже используемый суффикс `P` для подтем.

Пороги прохождения, распределение 50/30/20, целевая ветка Python и границы Core Python не меняются. Уточнение путей в разделе 10 и фактического статуса в разделе 11 не меняет обязательных критериев. Новые требования применяются к приёмке новых и пересматриваемых материалов; ранее созданные материалы получают отметку о недостающем до приёмки модуля, без молчаливой замены их содержания.

## 2. Версия и область применимости

**Обязательно:** целевая минорная версия курса — Python **3.14**, эталонная реализация для запуска примеров — **CPython 3.14** в обычной сборке с включённой глобальной блокировкой интерпретатора (GIL). **Рекомендуется** использовать актуальный стабильный исправляющий выпуск (patch release) ветки 3.14; точную версию, ОС и параметры сборки при проверке записывать **обязательно**. Ветка 3.14 выбрана как поддерживаемая; это зафиксированный выбор курса, а не требование всегда использовать последнюю ветку. Актуальный статус веток проверять по [Python Developer’s Guide](https://devguide.python.org/versions/).

Python как язык определяется синтаксисом и семантикой, описанными в [Language Reference 3.14](https://docs.python.org/3.14/reference/); CPython — одна из реализаций языка. Стандартная библиотека описана отдельно в [Standard Library 3.14](https://docs.python.org/3.14/library/). Поведение языка, библиотеки, ОС и реализации нельзя смешивать. Не все детали реализации гарантируются спецификацией языка; см. [введение в Language Reference](https://docs.python.org/3.14/reference/introduction.html).

**Обязательно:** обозначать зависимость утверждения и примера от версии, реализации, платформы и конфигурации там, где она существенна. Для CPython отдельно отмечать применимость рассуждений о [подсчёте ссылок и освобождении объектов](https://docs.python.org/3.14/reference/datamodel.html#objects-values-and-types), [сборке циклического мусора](https://docs.python.org/3.14/library/gc.html), [байткоде](https://docs.python.org/3.14/library/dis.html) и [GIL и сборке без него](https://docs.python.org/3.14/howto/free-threading-python.html); не обещать одинаковый байткод или момент освобождения объектов во всех реализациях. Даже внутри ветки 3.14 поведение отдельных функций `gc` зависит от patch release; для таких объяснений обязательна точная версия, а не только «3.14». Эксперимент показывает наблюдение в указанной среде, но сам по себе не доказывает гарантию языка. **Рекомендуется** обсуждать альтернативные реализации для сравнения; проверка всего курса на них не обязательна.

Переход на другую минорную версию (minor version) — отдельное изменение спецификации с проверкой совместимости материалов и примеров. Обновление patch release не меняет целевую ветку, но требует повторного запуска проверок.

## 3. Профиль выпускника и границы

Выпускник **обязательно** способен самостоятельно прочитать условие, уточнить неоднозначности, разбить задачу на части, написать читаемую небольшую программу, выполнить её, проверить нормальные и граничные случаи, локализовать и исправить ошибку, объяснить поведение и компромиссы решения. Он умеет пользоваться документацией и отличать известное от предположений. Для алгоритма он указывает модель входных данных и обоснованно оценивает время и дополнительную память в нотации Big O, где оценка применима.

В пределах Core Python выпускник объясняет и применяет:

- базовые конструкции, поток управления, функции и способы передачи аргументов;
- объекты, идентичность и равенство, изменяемость, ссылки и области видимости;
- встроенные типы и коллекции, итерацию, генераторы и протоколы;
- исключения, контекстные менеджеры, файлы, текст и кодировки;
- классы, экземпляры, наследование, композицию и основные элементы модели данных;
- модули, импорт, организацию небольшого проекта, виртуальное окружение и базовое использование пакетов;
- аннотации типов как средство описания интерфейсов и основы проверки типов, не предполагая автоматической проверки аннотаций при выполнении;
- базовые приёмы отладки, тестирования, анализа сложности и работы со стандартной библиотекой по документации;
- существенные для понимания программы основы исполнения и управления памятью CPython с обозначением границ этих объяснений.

Это карта компетенций и границ, **не последовательность и не учебный план**. Точный состав стандартной библиотеки и глубина отдельных механизмов определяются при разработке плана по результатам обучения. Основы конкурентности (concurrency), потоков, процессов и асинхронности допускаются как обзор моделей и ограничений; владение production-конкурентностью не является обязательным результатом Core.

За рамками основной программы: веб-фреймворки и разработка API, базы данных и ORM, фронтенд, DevOps и развёртывание, облачные сервисы, распределённые системы, безопасность как отдельная специализация, data science и машинное обучение, разработка расширений на C, глубокая оптимизация интерпретатора и сложные алгоритмы соревновательного уровня. Они могут стать самостоятельными последующими треками. Основы командной работы, Git и окружения полезны, но профессиональное владение инструментами не подменяет проверку Core Python.

## 4. Результаты по уровням

Уровни — последовательные контрольные состояния, а не названия утверждённых модулей. Каждое следующее включает результаты предыдущих. Оценка проводится по опубликованной рубрике и материалу, уже изученному учащимся.

| Уровень | Наблюдаемый результат | Доказательство достижения |
| --- | --- | --- |
| Beginner | Запускает программу, читает простые сообщения об ошибках, объясняет значения и поток управления, решает небольшие задачи с базовыми типами и функциями. | Проходит критерии соответствующих модулей и самостоятельно выполняет контрольную практическую работу с проверкой границ. |
| Foundation | Объясняет объекты и ссылки, использует коллекции, функции, исключения и файлы, читает и отлаживает код из нескольких функций. | Проходит критерии модулей и смешанную контрольную работу, включающую объяснение результата и исправление дефекта. |
| Junior | Создаёт небольшой структурированный проект с модулями, тестами и понятными интерфейсами; применяет ООП и протоколы по необходимости; объясняет сложность и ограничения. | Проходит критерии модулей и защищает самостоятельную работу по рубрике раздела 8. |
| Junior Interview Ready | Объясняет решения вслух, обосновывает выбор и область применимости утверждений, анализирует незнакомый код и корректирует ошибки после уточнений. | Выполняет итоговые критерии раздела 8, включая пробные собеседования. |

**Обязательно:** переход фиксируется только после выполнения всех подтверждений соответствующего уровня; успешный тест не заменяет практику или устное объяснение.

## 5. Формат и распределение усилий

**Обязательно:** плановая учебная нагрузка всей программы распределяется как **50% теория и механизмы, 30% практика и анализ кода, 20% интервью, тесты и контроль знаний**. Единица измерения — плановые минуты активной работы учащегося, включая чтение, выполнение и обратную связь. Каждый элемент учитывается ровно в одной основной категории по его цели: изучение объяснения — теория, самостоятельное решение или анализ — практика, оценочное тестирование или собеседование — контроль. Перерывы и организационное время не включаются. Допустимое отклонение при утверждении и после завершения программы — не более **±5 процентных пунктов для каждой категории**; журнал плановых и фактических минут обязателен. Если отклонение больше, владелец курса утверждает корректировку до следующего запуска. Отдельный модуль может иметь иное соотношение.

**Обязательно:** для каждой малой подтемы из плана подготовить подробную теорию; для каждого модуля — редактируемые слайды, карту «результат → подтема → слайд → задача», банк задач и анализа кода с независимыми проверками и эталонами, интервью-вопросы с рубриками, контроль и материал для повторения. Для итоговой самостоятельной работы обязательны условие, рубрика и инструкция по защите. Разбор типичных ошибок входит в теорию и проверку задач.

**Обязательно:** учебный маршрут малой подтемы строится как объясняющий блок с примером → посильная задача → разбор или обратная связь. Задача появляется до следующего блока, который опирается на изучаемое понятие. В слайдах каждого модуля соблюдается тот же порядок; подробная теория остаётся основным источником, а слайды дают компактную последовательность занятия. Короткое задание может ссылаться на задачу банка по её ID; текст и плановые минуты решения не дублируются. Время объяснения на слайдах относится к теории, самостоятельного решения — к практике, оценочного ответа — к контролю по правилу единственной основной категории выше.

**Рекомендуется:** справочный конспект, глоссарий, схемы, заметки преподавателя и подсказки с постепенным раскрытием. Их отсутствие само по себе не блокирует приёмку, если обязательные результаты и объяснения доступны.

## 6. Требования к качеству материалов

### Теория

**Обязательно:** для каждой темы и каждой малой подтемы указать устойчивый идентификатор, результат обучения и предварительные знания; в теории каждой подтемы объяснить «что», «зачем», «как работает», ограничения, типичные ошибки и применимые альтернативы, а также связать её с вопросами, практикой и контролем знаний. Проверка полноты проводится по каждому ID подтемы, а не по наличию общего обзора модуля. Новое понятие объясняется до использования или сопровождается явной ссылкой на уже изученное. Объяснение отделяет наблюдаемый результат от механизма и гарантии. Примеры минимальны, корректны для целевой версии и, где возможно, исполняются автоматически; ожидаемый результат и существенные условия воспроизводимости указаны. Ссылки ведут к конкретным разделам первоисточников, а не только на главную страницу.

### Слайды и последовательность применения

**Обязательно:** один комплект слайдов на модуль охватывает все его обязательные подтемы и результаты; `slides_plan.md` сопоставляет каждый результат с ID слайда, ID задачи и моментом её появления. Каждый слайд имеет постоянный ID и читаемые заголовок, код и объяснение; карта проверяется на отсутствие пропусков и ссылок на несуществующие задачи. После объясняющего блока каждой обязательной подтемы на слайдах следует посильная задача, использующая только изученные понятия, и возможность обратной связи до следующего зависимого блока. Исходник проверяется визуально при экспорте; если экспорт не запрошен или недоступен, приёмка Markdown-исходника не объявляется проверкой PDF/PPTX. **Рекомендуется** держать слайды краткими и добавлять заметки докладчика со ссылкой на подробную теорию.

### Вопросы и интервью

**Обязательно:** каждый вопрос привязан к результату и теме, имеет экспертный приоритет и критерии оценивания. Для интервью-вопроса предусмотрены краткий ответ, подробный ответ, возможные уточнения и признаки распространённых ошибок. Формулировка допускает проверяемый ответ и не требует ещё не изученного материала. Придуманные вопросы обозначаются как учебные; происхождение подтверждённых вопросов указывается с источником. Популярность не заявляется без проверяемых данных; экспертный приоритет не является статистикой.

### Задачи и анализ кода

**Обязательно:** для каждой задачи коротко, в одну строку задать, уровень сложности, формат входных данных и ожидаемого результата

## 7. Прохождение модуля и повторение

**Обязательно:** до начала модуля публикуются результаты, список предварительных знаний, состав оценивания, рубрика, пороги и условия пересдачи. До приёмки материалов модуля проверяются полнота теории по ID обязательных подтем, карта и исходник слайдов, существование указанных задач, порядок «объяснение → задача», интервью и контроль. Наличие ещё не принятого материала отмечается как пробел, а не как выполненное требование. Для зачёта учащегося одновременно нужны:

1. Все обязательные темы и материалы модуля изучены; все обязательные задания сданы.
2. Теоретический контроль — не менее **80%** доступных баллов; каждый обязательный результат представлен хотя бы одним оцениваемым элементом.
3. Практическая работа — не менее **80%** баллов по заранее опубликованной рубрике, включая корректность, граничные случаи, читаемость и объяснение. Независимые проверки обязательны; критический дефект в обязательном поведении не допускается независимо от суммы баллов.
4. Анализ кода и устное объяснение — не менее **70%** по соответствующей рубрике; учащийся объясняет как минимум один причинно-следственный механизм и исправляет выявленное существенное заблуждение.
5. Нет нерешённых критических пробелов в предварительных знаниях, влияющих на следующие результаты; преподаватель фиксирует доказательства, обратную связь и статус.

Критический дефект или пробел — заранее описанное в рубрике нарушение обязательного контракта либо фундаментальное заблуждение, из-за которого нельзя безопасно продемонстрировать результат. При неудаче учащийся получает адресную обратную связь, повторяет нужный материал и пересдаёт непройденные компоненты на эквивалентном варианте; число попыток не ограничивается этой спецификацией. Использование подсказок фиксируется: итоговая демонстрация самостоятельности проходит без них. Баллы не усредняются между компонентами для обхода порогов.

**Обязательно:** повторение строится по принципу интервального воспроизведения (spaced retrieval) и смешивания тем (interleaving). Рекомендуемый график после первого изучения: через 1, 7, 14 и 30 дней, затем раз в месяц до итоговой проверки. Плановые даты сдвигаются при пропуске; пропущенное повторение выполняется при первой возможности. Каждая сессия содержит самостоятельное воспроизведение и обратную связь; при ошибке назначаются целевое повторение и повторная проверка через 1–7 дней. Журнал хранит идентификатор результата, дату, итог, пробел и следующую дату. Соблюдение графика отслеживается, но само по себе не заменяет демонстрацию знаний.

**Обязательно:** проводить пробные собеседования минимум после достижения Foundation, после Junior и перед итоговой готовностью. Рекомендуемая продолжительность — 45–60 минут: объяснение, анализ кода и решение задачи с обсуждением. Рубрика и результаты фиксируются по компонентам; после каждого собеседования — конкретная обратная связь и план устранения пробелов. При неудаче итогового собеседования проводится повторное на другом эквивалентном наборе после доработки.

## 8. Измеримая итоговая готовность

Статус **Junior Interview Ready** присваивается, если выполнены все условия:

- Зачтены все обязательные модули и подтверждены результаты Beginner, Foundation и Junior.
- Итоговый смешанный теоретический контроль охватывает каждый обязательный результат программы хотя бы одним оцениваемым элементом; набрано не менее **80%** баллов и не менее **70%** по каждой группе результатов, определённой в утверждённом плане.
- Самостоятельная работа решает заранее заданную небольшую задачу, организована в модули, имеет инструкцию запуска и автоматические тесты обычных и граничных случаев. Независимая проверка обязательного поведения проходит полностью; по опубликованной рубрике набрано не менее **80%** за корректность, структуру, тесты, читаемость и объяснение. На защите учащийся может объяснить и изменить существенную часть своего решения без подсказки.
- На **двух последовательных** итоговых пробных собеседованиях с разными эквивалентными наборами учащийся получает не менее **70% в каждом** из компонентов: теория и механизмы, анализ кода, практическое решение и коммуникация. В каждом собеседовании набрано не менее **80% суммарно** при равном весе четырёх компонентов; критических ошибок по заранее объявленной рубрике нет. Одно из двух может быть собеседованием перед итоговой готовностью из раздела 7.
- Все выявленные критические пробелы устранены и перепроверены; журнал оценок, среда выполнения и обратная связь сохранены.

Итоговые проверки независимы от учебных примеров: наборы отличаются, но проверяют те же результаты и имеют сопоставимую сложность. Доступ к документации и инструментам заранее задаётся для каждого компонента; при проверке самостоятельности помощь другого человека и готовое решение не используются. Проходные баллы и рубрики отражают экспертные решения проекта и пересматриваются по результатам апробации.

## 9. Проверка технической точности и сопровождение

**Обязательно:**

1. Для каждого технического утверждения, где важны гарантия, версия или реализация, автор сохраняет ссылку на соответствующий раздел официальной документации Python 3.14; при необходимости дополняет принятым PEP или исходным кодом конкретной версии CPython. PEP проверяется на актуальность относительно документации и фактической реализации; исходный код подтверждает конкретную реализацию, а не общую гарантию языка.
2. При подготовке материала фиксируются дата проверки, точная версия интерпретатора, реализация, ОС и существенные настройки. Примеры с зависимостью от времени, случайности, файловой системы или порядка выполнения получают контролируемые условия либо допустимые варианты результата.
3. Все исполняемые примеры и эталонные решения запускаются на целевой версии; автоматические тесты проверяют вывод, исключения и граничные случаи, где это возможно. Неавтоматизируемые фрагменты проходят документированную ручную проверку. Команды проверки и результаты сохраняются вместе с материалом или в журнале проверок.
4. Второй проверяющий или отдельный независимый проход сопоставляет утверждения с источниками, а условие задач — с эталоном и тестами; ошибки исправляются до публикации. При единственном авторе независимый проход проводится отдельно после создания материала и фиксируется как самостоятельная проверка, без заявления о втором рецензенте.
5. При изменении версии Python или исправлении значимого источника проводится анализ затронутых материалов, повторный запуск и запись результата. Неопределённые утверждения помечаются и не выдаются за гарантии. Проверяются ссылки, соответствие утверждённому плану и отсутствие дублирования.

## 10. Стандарт файлов и идентификаторов

**Обязательно:** исходные материалы хранятся в Markdown (UTF-8); исполняемые примеры и тесты могут находиться в отдельных `.py` файлах. Идентификаторы неизменяемы после публикации и уникальны в пределах курса. Переименование заголовка или файла не меняет идентификатор; при переносе сохраняется карта перенаправлений. Удалённые идентификаторы не переиспользуются. Ссылки между материалами используют относительные пути и явные идентификаторы. Утверждённый план — отдельный документ, на который ссылаются материалы; изменение плана требует отдельного предложения и объяснения.

Рекомендуемая схема, согласованная с уже используемыми путями проекта и создаваемая только по мере появления соответствующих материалов:

```text
planning/course_spec.md
planning/curriculum.md             # проект плана до утверждения
planning/topic_tree.yaml           # машиночитаемые ID и зависимости
status.md                           # статус и передача контекста
Sxx-Myy/
  module.md                         # цели, зависимости, критерии
  theory.md                         # подробная теория по ID подтем
  slides_plan.md                    # карта результатов, слайдов и задач
  slides.md                         # редактируемый исходник слайдов
  interview.md
  exercises.md
  assessment.md
  examples/                         # исполняемые примеры и проверки
```

Рекомендуемый формат идентификаторов: `S01`, `S01-M01`, `S01-M01-T001`, `S01-M01-T001-P01` для малой подтемы; `S01-M01-SL001` для слайда и постоянные суффиксы `Q01` или `E01` для вопросов и задач. **Обязательно:** назначать ID каждому обязательному результату, подтеме, слайду, вопросу и задаче; если у подтемы один результат, её ID служит и ID результата, а при нескольких результатах каждому нужен отдельный постоянный ID. Номера назначаются один раз и не переиспользуются; порядок изучения задаётся планом, а не обязательно номером. Теорию можно разделять на файлы подтем при росте объёма, сохраняя ID и одну основную версию каждого объяснения. В заголовке каждого файла материалов указываются ID, название, статус, целевая версия, зависимости и дата последней технической проверки; для проверяемых утверждений и примеров — источники и среда проверки. Для `slides.md` служебные сведения могут быть в HTML-комментарии первого слайда, чтобы файл открывался непосредственно как презентация. Общие термины и объяснения имеют один основной источник внутри курса, остальные материалы ссылаются на него.
