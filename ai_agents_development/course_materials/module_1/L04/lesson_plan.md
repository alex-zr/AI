**Модуль:** 1. Рабочая основа

**Аудитория:** участники после L03  
**Предпосылки:** L01 — Git и границы; L02 — запуск функции; L03 — тесты и исправление  
**Артефакт:** две ветки от одного коммита, таблица критериев, обоснованный выбор  
**Приёмка:** [`practice_card.md`](practice_card.md), [`teacher_key/verify_l04.py`](teacher_key/verify_l04.py), рубрика [`../assessment.md`](../assessment.md)

## Наблюдаемые результаты

К концу занятия участник:

1. Готовит две попытки от одного базового коммита и записывает порядок запуска.
2. Добавляет необязательный параметр `greeting` так, чтобы старые и новые тесты проходили.
3. Сравнивает попытки по одной рубрике и отделяет ответ агента от ручных правок.
4. Выбирает вариант по проверенным фактам и формулирует предел вывода.

## Содержание

### 1. Вопрос сравнения

Сравнение отвечает не на вопрос «какой инструмент лучше вообще», а на вопрос:

> При одинаковом снимке, одинаковом запросе и одинаковых критериях какая из двух попыток дала проверяемый результат, и чем это подтверждено?

Один запуск не даёт права на общий вывод. Можно утверждать только то, что записано: в данных условиях получен данный diff, такие проверки, такие ручные правки.

### 2. Что удерживается одинаковым

- Базовая ветка и коммит.
- Файлы снимка.
- Текст запроса.
- Критерии и команда проверки.
- Лимит времени.
- Рубрика.

Меняется только среда. Если модель или режим разрешений отличаются, это записывается как различие условий. Нельзя называть сравнение «одинаковым», если одна среда получила подсказку или другой контекст.

### 3. Демонстрация 1: две рабочие копии

На демонстрационном репозитории:

```bash
cd demo/L04-base
git status
git log --oneline -1
git worktree add ../L04-opencode -b attempt/opencode
git worktree add ../L04-codex -b attempt/codex
git worktree list
```

Показать:

- обе ветки начинаются от одного коммита;
- `git rev-parse HEAD` в обеих копиях совпадает;
- основная ветка не меняется во время попыток;
- после попыток ветки можно сравнить через `git diff`.

Если `git worktree` недоступен в учебной среде, преподаватель заранее готовит две копии с ветками. Это фиксируется, а не маскируется.

### 4. Демонстрация 2: запись попытки

На демонстрационном файле `demo.txt` преподаватель показывает короткий запуск и заполняет одну строку журнала:

- среда и версия;
- режим разрешений;
- запрос;
- результат;
- diff;
- ручная правка;
- проверка;
- время, если измерялось.

Если среда не отвечает, используется заранее подготовленный diff, а в журнале явно указывается, что это демонстрационный материал, а не результат участника.

### 5. Как оценивать

Сначала факты:

1. Старые тесты проходят?
2. Новые тесты проходят?
3. Изменены только разрешённые файлы?
4. Старые тесты не ослаблены?
5. Diff понятен и минимален?
6. Ручные правки записаны?

Потом рубрика:

- A. Границы и безопасность.
- B. Результат и техническая корректность.
- C. Проверка и свидетельства.
- D. Сравнение и обоснование.

### 6. Выбор и предел вывода

Формула выбора:

> Выбран вариант X, потому что проверка Y дала Z. Вариант W отклонён, потому что... В данных условиях я не могу утверждать, что...

Если оба варианта равны по проверкам, допустимо выбрать тот, который проще объяснить и повторить. Это обоснование, а не подмена критериев.

## Вопросы на разбор

1. **Что вы удерживали одинаковым?**  
   Ожидаемые элементы: снимок, базовый коммит, запрос, критерии, команда тестов, лимит; менялась только среда.

2. **Где ответ агента, а где ваша правка?**  
   Ожидаемые элементы: diff, запись шага, причина правки; ручная правка не выдаётся за результат агента.

3. **Почему выбранный вариант лучше?**  
   Ожидаемые элементы: старые и новые тесты, границы файлов, понятность diff, проверка; вывод ограничен условиями.

## Типичные сбои

| Сбой | Признак | Действие |
|---|---|---|
| Разные базовые коммиты | `git rev-parse HEAD` отличается | Пересоздать ветки от одного коммита |
| Разный промпт | В журнале две разные формулировки | Использовать один текст, записать отклонение |
| Ручная правка скрыта | Diff не совпадает с ответом | Записать правку и причину |
| Старые тесты изменены | Diff в существующих тестах | Вернуть, добавить новые тесты |
| Обе среды запущены в одном сеансе | Контекст переносится | Новый сеанс, записать ограничение |
| Выбор «по ощущению» | Нет фактов и проверок | Заполнить таблицу, повторить выбор |

## Проверка и свидетельства

1. `git worktree list` — две ветки.
2. `git rev-parse HEAD` в каждой копии — один базовый коммит.
3. `python3 -m unittest discover -s tests -v` — пять тестов, код 0 в выбранной ветке.
4. `python3 teacher_key/verify_l04.py <путь-к-выбранной-копии>` — старые и новые требования.
5. `git diff` — только `greet.py` и `tests/test_greet.py`.
6. Журнал: две попытки, таблица, выбор, предел вывода.
